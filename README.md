# 电商店铺订单数据分析：RFM 用户分层与 GMV 结构

用 RFM 把 16.8 万成交用户分成 8 类人群，回答该挽留谁、该发掘谁。

数据范围 2024-01-01 ~ 2026-06-30，47.2 万条订单明细，6 个店铺；观察点 2026-06-30，RFM 窗口取近 12 个月。

## 为什么口径层放 SQL，而不是继续用 pandas

指标要进报告、要被反复引用，它的口径就必须固定在一处、可复现。具体三处收益：

1. **订单级去重的语义变清楚了**。原来的写法是
   `.groupby('订单id').agg(用户id=('用户id','first'), 下单日期=('日期','min'))`——
   `'first'` 取的是每组第一个**非空**值，与 `'min'` 未必来自同一行，
   这个口径其实是靠「一个订单只对应一个用户」这条数据巧合才成立的。
   换成 `ROW_NUMBER() OVER (PARTITION BY 订单id ORDER BY 日期, 商品id)` 取 `rn=1` 后，
   整行都来自同一条明细，语义自洽；补上 `商品id` 作第二排序键，
   是因为同一订单的多条明细日期相同，没有它 `ROW_NUMBER()` 的结果不保证可复现。

2. **口径只定义一处**。`v_成交订单`、`v_用户RFM`、`v_用户首单` 三个视图把去重键、
   R/F/M 与分档规则、首单判定固定下来，5 个指标文件全部引用它们，不会各写一遍。

3. **MySQL 没有中位数函数**。既无 `MEDIAN()` 也无 `PERCENTILE_CONT()`
   （后者是 Oracle/PostgreSQL 语法，MySQL 会报 1064），分档阈值按中位数的定义
   用 `ROW_NUMBER() + COUNT() OVER ()` 实现，见 `sql/00_schema.sql`。
   实现时踩到两个二次舍入的坑（`AVG()` 被物化后丢精度、除法默认只留 4 位小数），
   都写在 `sql/31` 的文件头。

反过来，**探索不搬**：数据分布、相关性、枚举取值、GMV 趋势这些一次性、试错性的分析留在
`py/EDA.ipynb`。它们本来就还没定出口径，提前固化成 SQL 只会挡住发现；
而一旦某个结论要进报告、要被反复引用，它就该从 notebook 沉到 `sql/`。

## 口径

- 统计对象与去重键：用户按 用户id，订单按 订单id，明细按 订单id + 商品id
- 业务状态：成交指订单状态「已完成」，已取消 / 已退款 / 待付款 / 待发货 / 已发货不计入
- 时间边界：月为自然月，RFM 窗口为截止观察点的近 12 个月
- 单位：金额 元，人数 人，比率 %
- 分档阈值：R / M 取窗口中位数（本数据 160 天 / 207 元），F ≥ 2 为复购；观察点与窗口长度定义在 `sql/00_schema.sql` 的 `v_用户RFM`，是该文件里唯一需要改的配置，本次运行的实际取值见 `data/metrics/rfm_阈值.csv`

## 已知局限

- 数据始于 2024-01，存在左截断：该月成交用户必然全部被判为新客，2024-01 的新客指标被高估，解读时须剔除该月；RFM 分层统一用近 12 个月窗口规避
- 明细金额 = 商品成交单价 × 数量 × 折扣率 只在多数行成立（原始 472,481 行中 386,668 行、81.84%；清洗后 454,466 行中 370,957 行、81.62%），实际成交价还含未记录的其他优惠，金额一律以 明细金额 为准
- 折扣率 实际只取 0 / 1，是折扣标记而非折扣比例
- **首单渠道对 173 个用户不唯一**：307 人首单当天有多笔订单，其中 173 人当天的流量渠道并不相同，
  「首单渠道」对这 173 人没有唯一答案（店铺维度无此问题，一个用户只属于一个店铺）。
  当前口径取 `订单id` 最小的一笔——这是一个选择而非事实；它与迁移前 pandas 的 `idxmin()`
  恰好落在同一笔上（已逐用户核对，168,360 人的渠道与下单日期 0 处差异），所以渠道维度的
  新客数没有引入偏差。该数字由 `dq_校验结果` 的「首单当日渠道有歧义的用户数」持续监控，
  一旦上升，渠道维度的新客数就需要重新解释。
